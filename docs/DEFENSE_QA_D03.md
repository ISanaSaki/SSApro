# راهنمای دفاع DEV-03 — فرانت‌اند و هوش مصنوعی (شبکه خون)

> این فایل برای آمادگی کامل ارائه و جلسه پرسش‌وپاسخ نوشته شده است.
> ساختار: معرفی کوتاه → سوالات فرانت‌اند → سوالات هوش مصنوعی → سوالات ترکیبی/چالشی → اعداد کلیدی برای حفظ کردن.

## ۱) معرفی ۳۰ ثانیه‌ای (اگر فقط یک دقیقه وقت داری همین را بگو)

بخش من دو تکه است:

1. **فرانت‌اند**: سه نمای کاربری (بیمارستان، مرکز انتقال خون، اهداکننده) به زبان فارسی و راست‌به‌چپ، با Vanilla JS و بدون هیچ وابستگی خارجی — کاملاً آفلاین. همه اعداد از API واقعی سامانه خوانده می‌شوند و هیچ عددی در رابط کاربری جعل نشده است.
2. **هوش مصنوعی**: یک مدل یادگیری ماشین محلی (رگرسیون لجستیک) که پیش‌بینی می‌کند کدام اهداکننده با احتمال بیشتری دعوت را می‌پذیرد؛ خروجی آن ترتیب دعوت موج را تعیین می‌کند تا با پیام کمتر، تأمین سریع‌تر تکمیل شود. اگر مدل به هر دلیلی در دسترس نباشد، سامانه خودکار به روش «نزدیک‌ترین اهداکننده» برمی‌گردد و هرگز از کار نمی‌افتد.

## ۲) سوالات فرانت‌اند

### س ۱: چرا از Vanilla JS استفاده کردی و React یا Vue نه؟

**چرا انتخاب کردم:** پروژه ۶ ساعته با قرارداد API ثابت است؛ سه صفحه با منطق مشترک (نمایش درخواست‌ها، تایمر، polling) نیاز دارد. Vanilla JS با ES Modules بدون هیچ مرحله build، بدون node_modules و بدون ابزار باندلینگ اجرا می‌شود — فقط فایل‌های استاتیک که FastAPI همان‌ها را سرو می‌کند.

**چرا فریم‌ورک نه:** ری‌اکت یعنی وابستگی به npm، حجم بالای bundle، نیاز به build و (در شرایط مسابقه) ریسک نبود اینترنت یا خطای toolchain. برای سه صفحه، سود فریم‌ورک کمتر از هزینه و ریسکش بود. منطق مشترک را هم در یک ماژول (`apiClient.js`) جمع کردم تا تکرار کد نداشته باشیم — همان کاری که یک فریم‌ورک می‌کرد، ولی ساده‌تر و شفاف‌تر.

### س ۲: چرا هیچ کتابخانه CSS یا آیکونی استفاده نکردی؟

**چرا انتخاب کردم:** شرط آفلاین بودن پروژه و ممنوعیت CDN. همه آیکون‌ها SVG داخلی (inline) هستند که در `apiClient.js` به‌صورت یک نگاشت کوچک تعریف شده‌اند؛ رنگشان با `currentColor` از تم پیروی می‌کند. CSS هم یک فایل دست‌نویس با متغیرهای طراحی (design tokens) است.

**چرا Tailwind/Bootstrap نه:** Bootstrap حجم و ظاهر از پیش تعیین‌شده دارد و شخصی‌سازی آن به تم قرمز/صورتی ما کار بیشتری می‌برد؛ Tailwind هم نیاز به build دارد. با CSS خالص، کنترل کامل روی تم، RTL و ریسپانسیو داشتم و حجم نهایی هم کمتر شد.

### س ۳: فونت پروژه چطور تأمین شده؟ چرا CDN نه؟

فونت **وزیرمتن (Vazirmatn)** را به‌صورت محلی در `static/fonts/` باندل کرده‌ام (چهار وزن 400/600/700/800 به‌صورت woff2 + فایل مجوز OFL — مجموعاً حدود ۲۰۰ کیلوبایت) و با `@font-face` لود می‌شود. این فونت نرم، گرد و دوستانه است و مخصوص متن فارسی طراحی شده. استفاده از فونت وب از CDN یعنی وابستگی اینترنتی — در شرایط مسابقه این ریسک است و قانون ما هم آفلاین بودن است؛ باندل محلی همان کیفیت را بدون هیچ درخواست شبکه‌ای می‌دهد. پشته نهایی: `Vazirmatn, Segoe UI, Tahoma, IRANSans` — اگر فونت باندل به هر دلیلی لود نشود، به فونت سیستمی برمی‌گردد (graceful fallback). `font-display: swap` هم باعث می‌شود متن هرگز پنهان نماند (بدون FOIT).

### س ۴: چرا تم قرمز/صورتی روشن انتخاب شد؟

سه دلیل: (۱) حوزه کاری خون است و قرمز رنگ طبیعی برند آن است؛ (۲) تصاویر مرجعی که از سایت سازمان انتقال خون گرفتیم دقیقاً همین زبان طراحی را دارد — هدر سفید، لوگوی قطره قلب، دکمه‌های قرمز کپسولی، کارت‌های صورتی ملایم؛ (۳) از نظر UX رنگ قرمز فقط برای «اقدام اصلی» و «هشدار» استفاده شده و بدنه سفید/صورتی ملایم است تا صفحه آرام و خوانا بماند (اصل سلسله‌مراتب رنگ). نسخه قبلی تم تیره‌تر سبز بود که با این مرجع بازطراحی شد.

### س ۵: چرا RTL و فارسی؟

کاربران سامانه ایرانی‌اند؛ `lang="fa" dir="rtl"` در HTML و استفاده از `inset-inline-*` و `margin-inline` در CSS باعث می‌شود کل چیدمان به‌صورت منطقی راست‌به‌چپ باشد. متن‌های UI فارسی‌اند ولی شناسه‌ها و enumها (مثل `red_cells`، `urgent`) انگلیسی مانده‌اند تا با قرارداد API یکسان باشند — این تفکیک عمدی است.

### س ۶: چرا polling و نه WebSocket/SSE؟

کیت مسابقه فقط REST دارد؛ ما نمی‌توانیم endpoint اضافه کنیم (قرارداد API فریز شده است). پس به‌روزرسانی زنده را با polling پیاده کردم: فهرست هر ۵ ثانیه، جزئیات هر ۳ ثانیه، ساعت شبیه‌سازی هر ۵ ثانیه. در مقیاس دمو این بار ناچیز است و ساده‌ترین راهِ قابل اتکا بود. اگر WebSocket در دسترس بود، همان را انتخاب می‌کردم — اما با قرارداد فعلی، polling تنها گزینه صحیح است.

### س ۷: اعداد داخل صفحات از کجا می‌آیند؟

همه اعداد از endpointهای `/api/*` خوانده و رندر می‌شوند؛ هیچ عددی هاردکد نیست. این یک اصل توافقی تیم بود (صداقت نمایشی): اگر API بگوید «کسری ۱۶ واحد»، صفحه همان را نشان می‌دهد. تنها استثناها متن‌های ثابت و شمارنده‌های اولیه «۰» پیش از اولین پاسخ API هستند.

### س ۸: توکن‌ها کجا نگهداری می‌شوند؟

در `localStorage` با کلیدهای مجزا: `bloodnet_hospital_token`، `bloodnet_coordinator_token`، `bloodnet_donor_id`. این برای دمو و ارزیابی هارنس ساده و کافی است. اگر سامانه تولیدی بود، توکن باید در httpOnly cookie می‌آمد تا در برابر XSS امن باشد — این را در دفاع اگر پرسیدند صادقانه بگو.

### س ۹: Idempotency-Key چطور در UI رعایت شد؟

درخواست ثبت خون باید idempotent باشد. کلاینت برای هر درخواست جدید یک کلید یکتا تولید می‌کند و در هدر `Idempotency-Key` می‌فرستد؛ ارسال تکراری (مثلاً دابل‌کلیک) درخواست دوم نمی‌سازد. این باگ را حین توسعه پیدا و رفع کردم — قبلش هدر اضافه ارسال نمی‌شد.

### س ۱۰: امنیت XSS چطور است؟

هر مقدار داینامیک (شناسه درخواست، نام، توضیحات، رویدادها) قبل از تزریق به DOM از تابع `escapeHtml` عبور می‌کند. یعنی حتی اگر داده مخربی از API بیاید، به‌صورت متن خنثی نمایش داده می‌شود نه HTML اجراشونده.

### س ۱۱: دسترس‌پذیری چه کارهایی انجام شد؟

برچسب‌های `aria-label` روی دکمه‌های آیکونی، `aria-live` روی ناحیه‌هایی که خودکار به‌روز می‌شوند (گرید درخواست‌ها و toastها)، `aria-current` روی تب فعال، نسبت کنتراست رنگ قرمز روی سفید، و احترام به `prefers-reduced-motion` برای کاربرانی که حرکت کم می‌خواهند.

### س ۱۲: ریسپانسیو چطور است؟

Grid کارت‌ها و فرم در عرض‌های ۹۶۰px و ۵۶۰px تک‌ستونه می‌شوند، نقاشی هیرو در موبایل حذف می‌شود، فوتر از ۴ ستون به ۲ و سپس ۱ ستون می‌رسد، و ناوبری زیر لوگو می‌آید. با Chrome واقعی (Playwright) هر سه صفحه در حالت موبایل تست و اسکرین‌شات شد.

### س ۱۳: چرا نوار پیشرفت سگمنتی (سبز/آبی/قرمز)؟

یک نگاه فوری سه چیز را نشان می‌دهد: واحدهای تحویل‌شده (سبز)، در حال تأمین/دعوت (آبی)، و کسری باقی‌مانده (قرمز). این دقیقاً همان «پیشرفت تأمین» است که کاربر بیمارستان باید در یک نگاه بفهمد. رندر آن CSS خالص است (سه span با عرض درصدی) — بدون کتابخانه چارت.

### س ۱۴: چرا مودال به‌جای صفحه جدا برای اصلاح/لغو؟

اقدامات مهم (اصلاح فوریت، لغو درخواست، رد درخواست) مخرب یا حساس‌اند؛ مودال با متن هشدار و دکمه تأیید مجزا، خطای کاربر را کم می‌کند و جریان کار را قطع نمی‌کند. انتخاب فوریت جدید هم با کارت‌های رادیویی (choice) انجام شده که هر گزینه مهلتش را توضیح می‌دهد.

### س ۱۵: چرا «این یک شبیه‌ساز است، نه سامانه پزشکی» نوشته شده؟

چون داده‌ها و قواعد سامانه کاملاً ساختگی و مخصوص مسابقه‌اند. نمایش این دیسکلیمر هم در فوتر و هم در صفحه اهداکننده، یک تصمیم اخلاقی/صداقتی است: کاربر نباید فکر کند با سامانه واقعی پزشکی کار می‌کند.

## ۳) سوالات هوش مصنوعی

### س ۱۶: اصلاً مشکل چی بود که AI لازم شد؟

وقتی درخواستی کسری دارد، مرکز باید از بین اهداکنندگان واجد شرایط، موج دعوت بفرستد (سقف ۸۰ نفر). اگر تصادفی یا فقط بر اساس نزدیکی دعوت کنیم، پیام‌های زیادی به افرادی می‌رود که پاسخ نمی‌دهند — این هم امتیاز «اسپم» را خراب می‌کند و هم تأمین را کند می‌کند. AI اینجا یک **مسئله رتبه‌بندی** را حل می‌کند: به هر اهداکننده امتیاز «احتمال پذیرش» بده و به ترتیب امتیاز دعوت کن.

### س ۱۷: چرا رگرسیون لجستیک و نه شبکه عصبی یا XGBoost؟

**چرا انتخاب کردم:** داده جدولی و عددی است (سن، وزن، سابقه، فاصله…)، حجمش ~۱۶۲ هزار رکورد است، و خروجی باید **احتمال کالیبره‌شده** بین ۰ و ۱ باشد — دقیقاً جایی که رگرسیون لجستیک استاندارد طلایی است. ساده، تفسیرپذیر، سریع (استنتاج در حد میلی‌ثانیه)، و فقط به sklearn نیاز دارد.

**چرا بقیه نه:** شبکه عصبی برای داده جدولی با این حجم، مزیت عملی چندانی ندارد و ریسک overfit و تنظیم‌پذیری بیشتری دارد. XGBoost هم گزینه معتبری بود و شاید AUC کمی بهتر می‌داد، اما وابستگی بیشتری اضافه می‌کرد و تفسیرپذیری‌اش کمتر است. در مسابقه ۶ ساعته، «مدل ساده‌ای که درست کار می‌کند و fail-safe دارد» بهتر از «مدل پیچیده‌ای که ریسک دارد» است. اگر زمان اضافه بود، XGBoost را به‌عنوان مقایسه امتحان می‌کردم.

### س ۱۸: چرا LLM یا API خارجی نه؟

سه دلیل: (۱) نیاز به API key و اینترنت دارد که با شرط آفلاین و بدون-هزینه ما در تضاد است؛ (۲) خروجی LLM غیرقطعی است و برای یک رتبه‌بندی عددیِ تکراری‌پذیر مناسب نیست؛ (۳) تأخیر و هزینه به‌ازای هر موج دعوت معنی ندارد، در حالی که مسئله ما یک پیش‌بینی عددی کلاسیک است. یادگیری ماشین کلاسیک برای این مسئله هم دقیق‌تر است و هم صفر هزینه.

### س ۱۹: ویژگی‌های مدل چیست و چرا این‌ها؟

سه گروه: **مشخصات اهداکننده** (سن، جنسیت، وزن، گروه خونی)، **رفتار تاریخی** (چند بار خبر شده، چند بار پاسخ/پذیرش/اهدای واقعی، نرخ پذیرش، میانگین تأخیر پاسخ)، و **زمانی/فاصله** (روزهای گذشته از آخرین اهدا، پنجره سکوت شبانه، فاصله تا مرکز). این‌ها همان چیزهایی هستند که یک انسان برای «حدس زدن پاسخ‌گویی» نگاه می‌کند؛ مدل وزن هرکدام را از داده یاد می‌گیرد.

### س ۲۰: «بدون نشت داده» یعنی چه و چرا مهم است؟

یعنی هر ویژگی فقط از اطلاعاتی ساخته شود که **در لحظه تصمیم‌گیری** وجود داشته است (تقسیم زمانی، نه تصادفی). اگر مثلاً از «نتیجه همان دعوتی که می‌خواهیم پیش‌بینی کنیم» ویژگی بسازیم، مدل در تست عدد عالی می‌گیرد ولی در واقعیت تصادفی عمل می‌کند. من داده را به‌ترتیب زمان split کردم تا ارزیابی صادقانه باشد — این را داورها خیلی دوست دارند بشنوند.

### س ۲۱: برچسب (label) مدل چیست؟

پاسخ دادن اهداکننده به دعوت (`responded`). چرا نه «اهدای موفق»؟ چون هدف اولِ موج‌دعوت این است که پیام بی‌پاسخ نماند و فرد وارد فرایند شود؛ اهدای موفق فقط بخشی از پاسخ‌دهنده‌هاست و نمونه مثبتش خیلی کم است. با برچسب responded، مدل داده مثبت کافی برای یادگیری دارد و مستقیم همان عددی را پیش‌بینی می‌کند که در معیار اسپم مهم است.

### س ۲۲: داده نامتوازن بود (فقط ~۱۲.۸٪ پاسخ مثبت). چطور مدیریت شد؟

مسئله ما رتبه‌بندی است نه کلاس‌بندی با آستانه؛ یعنی مهم نیست مدل «بله/نه» قطعی بگوید، مهم این است که بالای لیست، اهداکننده‌های پاسخگو باشند. بنابراین به‌جای accuracy، معیارهای رتبه‌ای (AUC و precision@k) را ارزیابی کردم که ذاتاً نسبت به عدم توازن مقاوم‌اند.

### س ۲۳: چرا precision@20 معیار ارزیابی است؟

چون موج دعوت محدود است (سقف ۸۰ نفر، معمولاً کمتر). سوال عملی این است: «اگر ۲۰ نفر اولِ لیست مدل را دعوت کنیم، چندتاشان پاسخ می‌دهند؟» این دقیقاً precision@20 است — معیاری که به کاربرد واقعی وصل است، نه یک عدد انتزاعی.

### س ۲۴: اعداد ارزیابی چه بود؟

- داده: ۱۶۲,۲۸۳ رکورد تاریخی اهداکننده
- AUC: حدود **۰.۷۷** (۰.۵ یعنی تصادفی)
- precision@20: حدود **۰.۴۵** — یعنی تقریباً نیمی از ۲۰ دعوت اول پاسخ می‌دهند، در حالی که بیس‌لاین تصادفی ~۰.۱۳ بود → **حدود ۳.۵ برابر بهتر**
- در مقایسه با روش «نزدیک‌ترین اهداکننده»: **حدود ۱۷٪ پیام کمتر** به‌ازای هر پذیرش — یعنی همان نتیجه با اسپم کمتر (مستقیم به امتیاز اسپم مسابقه کمک می‌کند)

### س ۲۵: چرا مدل آموزش‌دیده (`ranker.joblib`) را کامیت کردی؟

تا سامانه بدون هیچ مرحله آموزش، بلافاصله اجرا شود (مسابقه زمان‌بندی فشرده دارد)، آفلاین بماند، و در محیط داوری که داده آموزشی ندارد هم کار کند. حجمش هم کوچک است (کمتر از ۵۰ کیلوبایت). کنارش `feature_config.json` ترتیب ستون‌های ویژگی را فریز می‌کند تا نسخه آموزش و استنتاج هرگز ناهماهنگ نشوند.

### س ۲۶: چطور به بک‌اند وصل می‌شود؟

از طریق قرارداد تیم: DEV-01 در `app/config.py` دو تنظیم گذاشته — `ranking_strategy` (پیش‌فرض `travel_time`) و `ai_model_path`. اگر متغیر محیطی `RANKING_STRATEGY=ai_response` باشد، `app/main.py` استراتژی من را از `app.ai.ranking` می‌سازد. یعنی بک‌اند من را صدا می‌زند؛ من کد بک‌اند را دست نزدم — فقط پروتکل `DonorRankingStrategy` را پیاده کردم که در `app/domain/ranking.py` تعریف شده بود.

### س ۲۷: اگر مدل لود نشود چه اتفاقی می‌افتد؟

هیچ خطایی بالا نمی‌رود. استراتژی پرچم `available` دارد؛ اگر فایل مدل نباشد یا لودش خطا بدهد، به‌صورت خودکار به **رتبه‌بندی زمان سفر** برمی‌گردد (امتیاز = منفی دقیقه فاصله). حتی اگر وسط کار برای یک اهداکننده خاص خطا بخورد، فقط برای همان نفر fallback می‌شود. تضمین ما: خروجی AI هرگز بدتر از بیس‌لاین نیست.

### س ۲۸: چرا زمان سفر tie-breaker است؟

دو اهداکننده با امتیاز احتمال مساوی: دعوت از نزدیک‌تر منطقی است (سریع‌تر می‌رسد، SLA بهتر). پس مرتب‌سازی اول بر اساس امتیاز نزولی است و به‌عنوان معیار دوم، فاصله صعودی.

### س ۲۹: چرا `predict_proba` و نه `predict`؟

چون خروجی ما رتبه است نه تصمیم قطعی. `predict_proba` احتمال کلاس مثبت را می‌دهد که مستقیماً همان امتیاز رتبه‌بندی می‌شود. آستانه «دعوت کن/نکن» را بک‌اند و ظرفیت موج تعیین می‌کند، نه مدل.

### س ۳۰: چرا StandardScaler؟

رگرسیون لجستیک با گرادیان، به مقیاس ویژگی‌ها حساس است (سن بر حسب سال، وزن بر حسب کیلوگرم، تأخیر بر حسب دقیقه). استانداردسازی باعث همگرایی سریع‌تر و پایدارتر و وزن‌های قابل مقایسه می‌شود. در Pipeline با خود مدل باندل شده تا ترتیب transform همیشه درست باشد.

### س ۳۱: مدل کجا و چطور آموزش داده شد؟

`scripts/train_model.py` داده تاریخی هارنس را می‌خواند، ویژگی‌ها را با همان ماژول مشترک (`app/ai/features.py`) می‌سازد — یعنی کد آموزش و استنتاج از یک منبع واحد استفاده می‌کنند — مدل را آموزش می‌دهد و artifactها را در `app/ai/model/` می‌نویسد. ارزیابی هم با `scripts/evaluate_model.py` جدا و قابل تکرار است.

### س ۳۲: تست‌ها چه چیزهایی را پوشش می‌دهند؟

۹ تست در `tests/ai/`: بارگذاری واقعی artifact و نام استراتژی، رتبه‌بندی صحیح (همه اهداکننده‌ها برگردند، امتیازها در بازه ۰ تا ۱ و نزولی)، درست بودن ویژگی‌ها (مثل محاسبه روز از آخرین اهدا)، رفتار fallback وقتی مدل نیست، و پایداری در برابر ورودی خراب. همه ۹ تست بعد از مرج نهایی با master هم پاس شدند.

## ۴) سوالات ترکیبی و چالشی

### س ۳۳: AUC=0.77 «عالی» نیست؛ دفاع تو چیست؟

درست است — ولی این داده رفتار انسانی است که ذاتاً پرنویز است و بیس‌لاین تصادفی ۰.۵ و نرخ مثبت فقط ~۱۳٪ است. معیار تصمیم‌گیری من هم AUC تنها نیست: precision@20 حدود ۳.۵ برابر بهتر از شانس است و مهم‌تر از همه، **۱۷٪ کاهش پیام به‌ازای هر پذیرش** نسبت به روش فعلی بک‌اند (زمان سفر) — این دقیقاً همان چیزی است که امتیاز مسابقه (اسپم و SLA) اندازه می‌گیرد. به‌علاوه fallback تضمین می‌کند هیچ ضرری نسبت به بیس‌لاین ممکن نیست.

### س ۳۴: اگر مدل در عمل بد عمل کند چطور؟

معماری fail-safe است: بدترین حالتِ ممکن، برگشت خودکار به روش زمان سفر است — یعنی عملکرد دقیقاً برابر سیستم بدون AI. ما فقط وقتی مدل فعال می‌شود که artifact سالم لود شود و خروجی‌اش در بازه معتبر باشد. ریسک نامتقارن به نفع ماست.

### س ۳۵: چرا خودت موج دعوت نمی‌فرستی و فقط رتبه می‌دهی؟

چون تقسیم کار تیم است: منطق دعوت، دروازه ایمنی (ممنوعیت دعوت اهداکنندگان تعلیق‌شده) و ارسال پیام متعلق به بک‌اند (DEV-01) است. ماژول AI فقط یک تابع خالص «رتبه‌بندی» است که ورودی می‌گیرد و لیست مرتب برمی‌گرداند — بدون side effect. این طراحی هم تست‌پذیرتر است و هم ریسک تداخل با قواعد ایمنی بک‌اند را صفر می‌کند.

### س ۳۶: سخت‌ترین چالش بخش تو چه بود؟

دو تا: (۱) در فرانت، هماهنگ نگه‌داشتن سه نما با قرارداد فریزشده API و همه حالت‌های وضعیت درخواست (۷ وضعیت) بدون دست زدن به کد بک‌اند؛ (۲) در AI، جلوگیری از نشت داده در ویژگی‌سازی — چون راحت‌ترین راهِ «عدد خوب گرفتن»، غلط است و در داوری واقعی فاجعه می‌شد.

### س ۳۷: اگر دوباره شروع کنی چه چیزی را تغییر می‌دهی؟

برای AI حتماً XGBoost را به‌عنوان خط مبنا مقایسه می‌کردم و احتمالاً ensemble ساده LR+XGB را امتحان می‌کردم. برای فرانت، اگر قرارداد اجازه می‌داد، به‌جای polling از SSE استفاده می‌کردم. ولی با قیود فعلی (آفلاین، قرارداد ثابت، زمان محدود) همین انتخاب‌ها بهینه بودند.

### س ۳۸: چرا همه‌چیز باید آفلاین باشد؟

قید مسابقه است: بدون CDN، بدون فونت/آیکون/کتابخانه اینترنتی، بدون API خارجی. همه دارایی‌ها داخل ریپو است. این قید در هر دو بخش رعایت شده: فرانت فقط فایل استاتیک است و AI فقط یک فایل joblib محلی.

### س ۳۹: نقش تو در تیم دقیقاً چه بود؟

طبق سند تقسیم کار: کل `static/`، کل `app/ai/`، اسکریپت‌های آموزش/ارزیابی، تست‌های AI و مستند AI. به فایل‌های DEV-01 و DEV-02 دست نزدم؛ ادغام با کد آنها از طریق قرارداد (`RANKING_STRATEGY`) انجام شد و در گیت روی شاخه جداگانه `feature/d03-frontend` کار و در نهایت با master مرج شد.

### س ۴۰: چطور مطمئنی UI اعداد درست نشان می‌دهد؟

تست خودکار با Playwright روی مرورگر واقعی: هر سه صفحه باز شد، خطای کنسول صفر، و یک ممیزی DOM اعداد نمایش‌داده‌شده را با پاسخ API مقایسه کرد (همه یکسان). اسکرین‌شات‌ها هم برای بازبینی ظاهری ذخیره شد.
