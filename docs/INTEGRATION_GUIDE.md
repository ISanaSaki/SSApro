# سند یکپارچهسازی — BloodNet

**هدف:** اتصال امن سه بخش (Backend Core / Backend Data / Frontend+AI) به یک سرویس واحد قابل اجرا و قابل دفاع.
**مرجع نامها:** [docs/CONTRACT.md](CONTRACT.md) — هر تعارض با آن، به نفع CONTRACT حل میشود.

---

## ۱. ترتیب اتصال بخشها (ترتیب merge)

```
[1] d02 لایه داده      ←  هیچ وابستگی ندارد؛ همه روی آن میسازند
        ↓
[2] d01 هسته و API     ←  روی مدلها/ریپازیتوریهای d02؛ UI بدون d01 بالا نمیآید
        ↓
[3] d03 فرانت          ←  مصرفکننده /api/* ساخته d01 (میتوانست موازی با mock جلو برود)
        ↓
[4] d03 ماژول AI       ←  پیادهسازی Protocol ساخته d01 در app/domain/ranking.py
        ↓
[5] یکپارچهسازی نهایی  ←  اتصال استراتژی، e2e، smoke، مستندات، دمو
```

**چرا این ترتیب:** هر لایه فقط به لایه قبلی وابسته است؛ با این ترتیب هیچکس منتظر نمیماند و master همیشه قابل اجرا میماند.

## ۲. وابستگیهای بین بخشها (نقاط اتصال — همه از CONTRACT)

| از | به | از طریق | ریسک شکست اگر |
|---|---|---|---|
| d01 services | d02 repositories/models | امضای بخش ۸.۱ CONTRACT | نام متد/پارامتر تغییر کند |
| d01 main.py | d02 `init_engine`/`create_all`/`load_kit_data`/`get_session` | همان امضاها | loader امضای `KitData` را عوض کند |
| d01 main.py | d03 `app.ai.ranking.AIResponseRankingStrategy` | import داینامیک + Protocol | d03 کلاس را با نام دیگر بسازد |
| d03 فرانت | d01 `/api/*` و مسیرهای رسمی | DTOهای بخش ۹ CONTRACT | d01 فیلدی را کم/زیاد کند |
| d02 DECLARED/README | d03 `docs/ai_module.md` | تحویل سند | d03 مدل کامل نباشد → اعلام نمیشود |

**قاعده طلایی:** هیچ نقطهای خارج از این جدول نباید وجود داشته باشد. اگر d01 به متد جدیدی در data نیاز داشت → درخواست به d02 → اضافه با تست → merge. نه ویرایش مستقیم.

## ۴. سناریوهای تست یکپارچگی (جلسه نهایی — همه اعضا)

### I1 — اجرای یکدستوری از محیط تمیز
```bash
git clone <repo> /tmp/bloodnet-fresh && cd /tmp/bloodnet-fresh
scripts/setup.ps1 && scripts/run.ps1
```
معیار: سرویس روی :8000 بالا میآید؛ `GET /health` → `{"ok": true}`؛ بارگذاری کیت زیر ~۱۵ ثانیه.

### I2 — قرارداد رسمی
`python -m harness.contract_tests --team http://127.0.0.1:8000` → همه PASS (شامل همزمانی ۲۰ تایی و replay).

### I3 — سه سناریوی تمرینی
```bash
python -m harness.runner --team http://127.0.0.1:8000 --scenario P-normal --seed 1000
python -m harness.runner --team http://127.0.0.1:8000 --scenario P-amend --seed 1000
python -m harness.runner --team http://127.0.0.1:8000 --scenario P-abuse --seed 1000
```
معیار: هر سه کامل اجرا میشوند؛ `safety=1` در هر سه؛ `score_0_100` منطقی نسبت به baselines؛ در P-abuse درخواست H98 رد شده و burst در pending_review مانده است.

### I4 — گام طلایی UI (مرورگر واقعی)
بیمارستان H07 → ثبت درخواست → (در صورت pending) تأیید توسط مرکز → مشاهده dispatch در جزئیات → اهداکننده D00001 دعوت را میپذیرد → arrived → donated → نمای بیمارستان `fulfilled` را نشان میدهد → در صورت تکمیل، دعوتهای باز `not_needed` میگیرند. معیار: اعداد UI با `GET /requests/{id}` یکساناند (صداقت اعداد).

### I5 — ایمنی (Safety Gate)
در خروجی هر سه سناریو: **صفر** پیام به اهداکنندگان دارای تعلیق فعال/خارج از شرایط. روش: شمارنده log در invitation service + بررسی مجدد `notifications` مقابل `donor_events` با یک اسکریپت موقت. (این تست حیاتی است: خطا = صفر کل امتیاز.)

### I6 — ریاستارت و re-drive
وسط اجرای P-normal سرویس را بکش و دوباره بالا بیاور: شمارندههای درخواستهای موجود از DB بازیابی میشوند؛ وظایف pending از جدول tasks دوباره اجرا میشوند؛ هیچ پیام تکراری با notification_id جدید به یک donor برای یک request ارسال نمیشود.

### I7 — ماژول AI (فقط اگر کامل است)
دو اجرای P-normal با `RANKING_STRATEGY=travel_time` و `RANKING_STRATEGY=ai_response`؛ مقایسه `notif_per_unit`. اگر بهبود واقعی و مستند بود → اعلام در DECLARED؛ وگرنه → حذف از DECLARED و ماندن روی travel_time (بدون جریمه).

## ۵. هماهنگی مدیریت خطاها (بازبینی متقابل)

- همه پاسخهای خطای API قالب `{"error":{"code","message"}}` دارند (چک با تست قرارداد).
- فرانت هیچ خطایی را قورت نمیدهد: هر کد خطا toast فارسی مشخص دارد (نگاشت در `apiClient.js`).
- خطای سرویسهای کیت: retry محدود + ثبت در DB (وظیفه/دیسپچ) — کاربر هرگز منتظر نمیماند و پاسخ HTTP هیچوقت بهخاطر کیت hang نمیشود (timeout).
- logging استاندارد در `logs/service.log`؛ پیامهای انگلیسی؛ سطح از env.

## ۸. بررسی نهایی اجرا و استقرار (قبل از commit نهایی)

2. سه سناریو (I3) + safety (I5).
3. دموی کامل UI یکبار از ابتدا (I4).
4. `DECLARED.md` در برابر قابلیتهای واقعاً نمایشدادهشده بازبینی شود (هر ادعای غیرقابل نمایش حذف شود).

6. SHA و زمان commit نهایی ثبت شود (تحویل = آخرین commit).
